# Phase 1 · Workstream A · `apps/api`

## Status

Every route is under **`/api/v1`** (nothing is served on `/api`) and tested: vitest against a real Postgres test database, through `fastify.inject`. Extraction runs through a port. The **fake adapter** fakes only the AI: page images, the PDF's text layer and the evidence binding are the real `@dct/extraction` code.

Since 2026-10-28 the API implements the review workflow of ADR-001 (`docs/phase-1/adr-001-extraction-evidence.md`), step 5 "backend wiring", and since 2026-10-29 the review lists of its §6 (interpretations, the bill-by-hand list; the blind sample was removed by ADR-003). Every number is checked against the PDF's own text, a person answers what didn't check out, shown our reading and what we suggest (ADR-003), and approval is gated on those answers.

## How to run

```sh
pnpm install
apps/api/scripts/db.sh start          # Postgres 16 in Apple `container` "dct-postgres", port 5434; creates dct_finance, dct_finance_test, dct_finance_e2e
pnpm --filter @dct/api db:migrate     # drizzle migrations (DATABASE_URL from repo-root .env)
pnpm dev:api                         # tsx watch: http://127.0.0.1:4100/api/v1 (real AI reads cost money)
pnpm --filter @dct/api test           # uses dct_finance_test, temp UPLOAD_DIR, fake extraction
pnpm --filter @dct/api typecheck
pnpm --filter @dct/api lint           # ESLint (un-awaited Drizzle queries and promises)
pnpm --filter @dct/api db:check       # schema.ts and the migrations agree (no database needed)
```

Production (no tsx):

```sh
pnpm --filter @dct/api build          # tsup → apps/api/dist (server.js, db/migrate.js)
pnpm --filter @dct/api db:migrate:dist   # node dist/db/migrate.js: a separate release step, before starting
pnpm --filter @dct/api start          # node dist/server.js
```

`db.sh stop` stops the container and `db.sh reset` deletes and recreates it. The script only touches `dct-postgres`.

**Settings** are environment variables, every one listed with its default in the repo-root `.env.example`. Variables already set win over `.env`. They're checked once at startup with zod (`src/config.ts`): a bad or missing one stops the API before it listens or connects, with a list naming each bad setting and what it must be, never its value (`DATABASE_URL` and the API keys are secrets). An empty value counts as unset. The reading's own settings (`EXTRACTION_MAX_USD`, `EXTRACTION_GRID_DPI`, `CROSS_READ*`, `OPENAI_*`) are read by `@dct/extraction`, but checked here too, so a typo fails at startup instead of silently falling back to a default. `ANTHROPIC_API_KEY` (unless `EXTRACTION_FAKE=1`) is checked only when the server starts (`readingProblem`, called by `src/server.ts`): the migrator, `e2e-reset` and the tests never read a contract, so they don't need it. Outside the repo checkout, `DATABASE_URL` and `UPLOAD_DIR` are required: their defaults are the local dev database and `<repo>/data/uploads`.

The web's Next rewrite forwards `/api/:path*` to the API unchanged, so `/api/v1/...` needs no proxy change.

## Routes

All under `/api/v1`. Bodies and responses are the types in `packages/shared` (`api.ts`, `evidence.ts`, `search.ts`, `alerts.ts`). Errors are `{ statusCode, error, message }`: `error` is the status's name ("Conflict"), `message` plain English. Every POST and PATCH takes an `Idempotency-Key` header (below). Every response carries `X-Request-Id`, the id in its log lines and in a 5xx message's "ref".

## Layout

- `src/db/schema.ts` defines the tables: studies, documents, study_documents, rulebook_versions, jobs, idempotency_keys, audit_log, alerts, alert_reads, settings. `pnpm --filter @dct/api db:check` (`scripts/db-check.ts`) fails if it and the migrations disagree.
- `drizzle/0000_init.sql` is generated. `drizzle/0001_guards.sql` is custom: an append-only trigger on audit_log, an immutability trigger on signed versions, and the settings row seed. `drizzle/0005_talented_slyde.sql` adds the review columns and replaces the immutability trigger (below).
- `src/extraction/port.ts` holds the `@dct/extraction` interface and adapter selection. `fake.ts` holds the synthetic rulebook and checks.
- `drizzle/0009_idempotency_and_one_live_read.sql` adds `idempotency_keys` and the one-live-read index on `jobs` (first failing an older live read of a version beside a newer one, so the index can be built).
- `src/jobs.ts` holds the pg-boss queues `identify` and `extract` with their handlers, `stranded` (pg-boss's dead letters) and `maintenance`.
- `src/lib/idempotency.ts` holds `write()`: one transaction per write, with its Idempotency-Key.
- `drizzle/0010_perfect_virginia_dare.sql` adds `rulebook_versions.warnings` and turns maker-checker on by default; `drizzle/0011_truncate_guards.sql` refuses TRUNCATE (below).
- `src/review.ts` holds the questions built after a read (`reviewDraft`) and `answer`, a thin wrapper that throws `answerQuestion`'s refusal as an `HttpError`. The rules themselves are in `@dct/shared`, so the web shows them by the same code: answering, follow-ups, typing done, the gate and the diff (`answer.ts`), contract problems as questions (`problems.ts`), the interpretations, one-value questions and the sample (`questions.ts`), search (`search.ts`).
- `src/domain.ts` holds DTO mapping, the study-status derivation, the draft guard, and carrying corrections into amendments.
- `src/lib/pointer.ts` handles JSON-pointer edits (a bad pointer is a 400). The labelled structural diff and value labels are `diffRulebooks` and `labelFor` in `@dct/shared` (`diff.ts`).
- `src/routes/*.ts` holds the HTTP routes.

## Review questions (ADR-001)

**After a read** (`runExtract` → `reviewDraft`): every document's text layer is read (`readTextLayer`), each money value is bound to its own spot (`bindEvidence`), and the questions are built (`reviewFromEvidence` plus the rest). The version stores `evidence`, `review` and `pdfCheck` (`{ values, matched }` over the values on text pages; null when no value sits on a text page).

The questions, in order:
1. **Values** (`confirm_value`, blocking): every value in `conflict` (the PDF prints something else there) or `ungrounded` (nothing found), typed.
2. **Money terms the master doesn't hold** (`unaccounted`, blocking, from the inventory sweep; `term` holds their words and figures): bill by hand, not a payment term, or already covered. "Bill by hand" lists the term on the master's `unclassified` list, from its own words; any other answer, or a send-back, takes it off again. There is no "add it to the master": nothing can add a value to a read draft, so that pick would drop the term silently.
3. **Contract problems** from `runContractChecks`, one question each. A blocker is settled by a typed value or a pick (I6); a Review question by a pick or a fixed reason with a note (ADR §6). An option with a `note` asks for one, in those words ("What should we ask the sponsor?").
   - `GRID_CONFLICT`: one question per arm, `path: null` (a choice). The pick sets that arm's grid in `governingGridIds`; the other arms' picks stay. Not asked for an arm whose choice an amendment carried. The check compares whole grids (`gridPrices`): two that differ in a single cell conflict; two that price everything the same are billed once (`billedGrids`), with nothing to ask. Grids that differ bill nothing until one is chosen, and approval is refused meanwhile ("Choose which budget grid to bill for …"). Asked again after an answer: a number written into one of an arm's grids (a typed answer, a correction) that makes them differ asks that arm's `GRID_CONFLICT` (`gridConflicts`), unless a grid is chosen for the arm or its question is open.
   - `AMBIGUOUS_TERM` on an interpretation field is that interpretation's question, marked (item 4). On any other single value, and `REQUIRED_MISSING` on one value: pick from the field's list, or type it (`interpretation` / `confirm_value`, blocking).
   - Totals that don't add up (`VISIT_TOTAL_MISMATCH`, `PER_PATIENT_TOTAL_MISMATCH`, Review): which number governs, the total as printed or its parts added up (offered when the sum can be worked out), each with a note for the sponsor. Each writes its own number into the master, logged like a correction, so an amendment carries it, and either can follow the other:
     - "The sum" writes the parts added up as they are now.
     - "As printed" writes the total the contract prints, kept on the question (`asPrinted`): the read's total when the question was asked, or, once a person types that total (a correction, a sample, "This looks wrong"), what they last typed. Never the sum.
     - A question stored before `asPrinted` existed falls back to what the read's check found printed (`detail.actual`), but not for a visit's subtotal, whose check adds in the non-procedure amount. Where neither says, "as printed" is refused (409), and "This looks wrong" on the total, typed as printed, asks the question again with it.
     - A settled total is asked again (`review.reopened`, "Total asked again") once its answer no longer holds: a part it adds up from changed, or another answer wrote the total (the finding then reads differently). Otherwise billing would take a sum of numbers since corrected.
   - `OVERHEAD_LABEL_MISMATCH`: the printed amounts (the label is wrong), or ask the sponsor (note). `DUPLICATE_ITEM` (only the same procedure twice within one table: two rows of a grid priced at the same visit, or the same invoiceable listed twice; never a grid price beside an invoiceable of that name): bill both, or ask the sponsor (note). Neither writes anything: the printed amounts stand.
   - `MISSING_REFERENCED_DOC`: "upload later" or "doesn't affect billing" (note). One per missing document, except on an amendment uploaded without the agreement it amends (no master agreement, work order or adoption in the study): then one non-blocking item (`path: null`) names the missing agreement and lists every document referenced and not uploaded.
   - No question has one possible answer (ADR-003 C3). A check whose answer would change nothing in the master is a **notice**, not a question (`isNotice`, `notices` in `@dct/shared` `problems.ts`): a grid header naming another investigator or site (`HEADER_MISMATCH`), a grid's total for several patients (`MULTI_PATIENT_ESTIMATE`: nothing is billed from it), and wording flagged as unclear where no field holds the reading (`AMBIGUOUS_TERM` with no value at its path). The web lists notices with the reading's warnings ("Worth knowing") beside the questions, after a read and at approval. `UNREADABLE_PAGE` is asked like a scanned page (`PAGE_OPTIONS`: nothing the master doesn't hold, or list the page to bill by hand). Anything else (`REQUIRED_MISSING` without a value, and the other Review checks): "bill it as printed" or "ask the sponsor", each with a note. A pick the API can't carry out (remove a grid, bill a duplicate one way) isn't offered.
   - Blocking when the check's severity is `blocker`, and for `AMBIGUOUS_TERM` and `REQUIRED_MISSING` (ADR §6).
   - Not asked: `AI_DISAGREEMENT`, `TEXT_LAYER_MISMATCH`, `LOW_CONFIDENCE` (ADR §4: not evidence; the binder replaces them), and a total that doesn't add up while a number in its grid is being typed (one flag per root cause; per grid for now; `recheck` asks it once the grid's numbers are answered).
4. **Interpretations** (`interpretation`, reason `INTERPRETATION`, blocking; `interpretations` in `@dct/shared` `questions.ts`). Two tiers (ADR-002 §4): a clause that **states a parameter outright** isn't asked; a **genuinely ambiguous or silent** one is. *Explicit and confirmed* is mechanical: the read gives a value other than "not stated" and the clause's exact quote; the figure that decides the field (`Field.stated`) is `confirmed` or `confirmed_by_math` in the evidence (the binder confirms a figure only inside that quote on the cited page); no `AMBIGUOUS_TERM` or `RETROACTIVE_NO_DATE` is about it. Today that is a cap's kind when it is an amount (its limit is a confirmed dollar figure) or a ratio (its ratio is confirmed) on an invoiceable, and the start date when it is given and confirmed. Those values are ordinary confirmed ones: nothing is asked about them. Everything else keeps its question: overhead scope, how visits are paid, each site fee's trigger, a count or blocks cap, every screen-fail term, the holdback's scope and rounding (the binder confirms no word of an enum, so nothing says the clause stated it outright). The questions asked are: overhead scope, how visits are paid, each site fee's trigger, each cap's kind (only where the kind isn't `none`), the screen-fail basis, cap kind and how screen failures are paid, what the holdback is taken from (typed: it's free text), rounding, and the start date. Picked from the field's own values, next to its quote nothing preselected; our reading is shown and suggested (`suggest`). While a cap's kind is asked its limit and ratio wait for it; once it's answered, the limit (or a ratio cap's ratio) is asked (`cap:`) if it wasn't confirmed, if the kind changed (`CAP_KIND_CHANGED`), or if the kind needs a figure the master doesn't have (`REQUIRED_MISSING`). "No limit" drops the cap's figures and their evidence, and closes every question still open about them (`review.closed`, "Question closed"); after that a limit or ratio there is refused (409) whether answered, reported or typed by hand, until the kind is changed. A site fee's trigger isn't asked either when its amount is confirmed and its table row prints, right of that amount, words naming exactly one trigger, the read's (`besideOnLine` in `@dct/extraction`, `triggerOf` in `@dct/shared`, passed by `reviewDraft` as `printed`; ADR-003): "one-time payment", "per year", "per sample". Vague words ("paid per terms of the exhibit") or another trigger than the read's keep the question.
   - **Rounding** (owner, 2026-11-02): asked only when the contract says something about it: the read quotes a clause (`rounding.prov.source.quote`), or the contract's text mentions rounding anywhere (`reviewDraft` passes `roundingSaid`: "rounded", "rounding", "round up/down/off/to", "nearest dollar/cent", "whole dollars"; a page nothing searched, a scan with no reading, leaves it unknown and asked), or an `AMBIGUOUS_TERM` is about it. Otherwise it's a notice, not a question: "The contract doesn't say how amounts are rounded, so printed figures are billed to the cent." (`notices` with the version's questions and evidence: shown while no question asks it and nobody answered it, on a read contract, never one typed by hand). Versions read before keep their rounding question.
   - **A date tied to the last signature** (the effective date, as `AMBIGUOUS_TERM` or `REQUIRED_MISSING` on `/study/effectiveDate/value`, or an amendment's start date that isn't retroactive), asked while the read gave no date (one it gave is checked like any value): when its quote or the read's flag about it ties it to signing ("the date of last signature", "upon full execution"; not "retroactive", "regardless of"), and the cited document has pages the read excluded as `esign_certificate`, the question is worded by us ("The contract takes effect on the date it was last signed. Its e-signature record is page N of “file”. …"), never the read's "the signature page isn't provided", the record's page comes first in `where`, and `signedOn` = `{ date, page, printed }` holds the latest date of signature the record prints (`lastSigned` in `@dct/extraction`, through the port; text pages only; an all-number date that reads two ways gives none unless the record shows the order). It is what we suggest; it's never written to the master, never evidence, and never confirms anything by itself: taking it is typing it (`chosen`, attested to the person). A record that gives no one date, a scanned record, a contract signed in ink (no record) or an older port (no `lastSigned`): no suggestion.
   - **Two dates for the effective date** (`SIGNED_DATE_DIFFERS`, `contract_problem`, blocking, id `signed:/study/effectiveDate/value`): a consistency check beside the above. When the master holds an effective date, whatever its evidence (confirmed or open), the date is tied to signing by the same rule, and the cited document's e-signature record gives a latest date of signature that differs, one question shows both dates with their pages (`where`: the date's spot, then the record's page) and suggests neither: page 1 may print a "dated as of" date that governs. Its two options are the two ISO dates; a pick writes the date picked (attested to the person, logged like a correction). Code never changes or downgrades the stored date. Equal dates, no record, a record giving no one date, or a clause that doesn't tie the date to signing ("entered into as of March 4, 2024"): no question. `reviewDraft` gets the excluded pages with their kinds from `jobs.ts` (`out.pages.filter(isExcludedPage)`); a replay gets them from the stored version's pages or its `pages_excluded` warning.
   - **Start date**: asked on any amendment read (the study has a live version, or a document is an amendment), on a retroactive one, and whenever `appliesFrom` is set. With no date it's `RETROACTIVE_NO_DATE`, a blocker. Either way it's answered by typing the date, or by picking "prospective only" (`prospective`, offered on any amendment read) and typing the amendment's own date as printed on it: where the read gave no start date it's checked against the read's date of the newest amendment document (`amendmentDate`). What's written is the date the person typed; a date the AI read is never written as attested. A stated date is checked like any interpretation.
5. **Pages**: a scan page (`image_only` or a scanner's `ocr_layer`) can't be swept, so a person attests it (`SCAN_PAGE`, blocking, I5); so does a text page with a picture big enough to hold prices (`PICTURE_PAGE`, from `TextPage.largePicture`). "List this page to bill by hand" needs a note naming each term. A text page with invisible words gets a warning in the version's `warnings` (never a question: those words are never evidence, ADR-003 C3).
6. **Corrections an amendment's read couldn't carry** (anything skipped but `already_equal`): each is said in `warnings`. One about a value billing reads is asked where the value is now (`CORRECTION_NOT_CARRIED`; a moved item found by its identity), unless it's asked already; one the new read doesn't have at all asks whether it's still in the contract (`CORRECTION_LOST`: removed, or bill by hand with a note).
7. **No blind sample** (ADR-003, 2026-11-01): a value the PDF's text or the contract's own totals confirm asks nothing. Versions read before keep any `SAMPLE` questions they hold, answered like any other value question.
8. **A table's columns** (`TABLE_CHECK`, blocking, `path: null`): a scanned table whose printed headers don't match the read's visit names but whose columns line up with the visits by count and order. The binder holds its prices (`ValueEvidence.held` = the check's id, status still `conflict` / `ungrounded`), and `reviewDraft` asks two picks per table (`tableQuestions`, drawn through `sampling`): "Which visit is the highlighted column of the table on page N?", the column's box in `where`, the grid's visits in order as options, none preselected; two different visits, columns with held prices first. The read's visit for the column is kept on the stored question (`table.expect`) and sent: it's what we suggest.
   - Every held price waits while it is held (`openPaths` takes `evidence`: `held` counts like an open question): marked "needs you", its evidence without printed text until the check settles. The pick's id is its place in a random draw (`table:<check>:<0|1>`), never its column's position, and the two picks are listed in that random order.
   - Only a pick of one of the listed visits settles a pick: an empty answer, free text, a value or a note is a 400, and a question with no expected visit (the binder's placeholder) is a 409. "Can't tell" rejects the mapping, as a wrong pick does.
9. **A table's blank items** (`BLANK_INVOICEABLE`, blocking, `path: null`, id = the binder's `blankChecks` id): the read marks cells "invoiceable" that a drawn table prints blank (a text page, or a clear scan; no word or unread ink in the cell). The binder marks each cell's evidence `blank` (status stays not confirmed, no per-cell question) and `reviewDraft` asks one pick per table (`blankQuestions`): "On page N, the highlighted items print no price at the scheduled visits. How are they billed?", the table's box and each row's in `where`, options "Only where the contract prints a price" / "At every scheduled visit shown", none preselected. The cells wait while it's open (`openPaths`: `blank` counts like `held`). Answered through the ordinary answer route (`answerQuestion` → `answerBlank`): "only where printed" removes every cell of the group from the grid and drops their evidence (audit `review.blank_removed`; the person is an editor), "every scheduled visit" makes them `attested`, "can't tell" makes each cell an ordinary value question (`BLANK_REJECTED`, audit `review.blank_rejected`). Only a listed pick answers (a value, a note or an unlisted option is a 400); a settled pick is final (409) and can't be sent back; the grid's totals are checked again after a removal (`recheck`, `gridConflicts`). On a table whose columns are only held (it has a `TABLE_CHECK`) the group waits for it (`after` = the check's id, shown to the web): answering it is a 409 "Confirm the table's columns first" until every column pick is right (`after` is then cleared), and a rejected table (a wrong pick, "can't tell", or no columns to pick from) rejects the group too, its cells becoming `BLANK_REJECTED` questions as `rejectTable` does for held prices. A table with agreed columns has no `after`.
   - Every pick right: in the answer's own transaction (`followUps` → `settleTable`) every held price becomes `confirmed`, noted "Checked by <who>: the table's columns were confirmed, and our own reading of the scan agrees", and `review.table_confirmed` is logged.
   - Any pick wrong: the mapping is rejected for good (`review.table_rejected`). Each held price loses `held` and becomes a "type what's printed" question (`TABLE_REJECTED`, id `held:<path>`), and an unanswered pick of the table closes. A pick that settles is final: answering it again is a 409, and it can't be sent back (use "This looks wrong" on a price). A table with no column to pick (`rejectTable` in `reviewDraft`) is rejected at once, so held prices are never stranded.
   - A held price is never `confirmed` until then, so the gate refuses sign-off with its open picks, and with any held price left. Whoever picks is an editor (maker-checker).

**Anomalies and review items.** The checks' anomalies are kept on the version as the record of what was found at read time; they are never resolved and don't gate approval. The review items are the workflow and the gate.

**Scans** (ADR §3 scan mode): no text layer, so `pdfCheck` is null and every money value on a scan page is typed (`SCAN_VALUE`), with one exception. A grid value is `confirmed` by the contract's own totals when they agree **to the cent**: the visit's parts add up to its total and its cells to its subtotals, a per-patient total is the sum of every visit, and a unit price equals a checked cell of its row. `DocumentDto.text` is `"scan"`, and the web asks for the e-signed original.

**Answering** (`answerQuestion` in `@dct/shared` `answer.ts`; then `followUps` adds what the answer asks next):
- A typed value is compared with the PDF's text at its spot (`evidence.printed`: an amount or percentage read by `parseCents` / `parsePercent`, a sentence's full stop after it dropped; a date as the binder reads it), or, where nothing parseable is printed, with the value we hold. Same → `matched`; else `differs`, and `compare = { typed, read, printed }` is filled for that item only. Where the evidence is a `conflict` and nothing printed parses (the page prints several figures, none of them ours), our reading is no truth: every first answer is `differs`, and `suggest` offers nothing to take.
- Answering a `differs` item with the same value (or pick) again, or with the PDF's own, settles it as `chosen`, and needs a note; any other value is a new answer, checked again:
  - Where the PDF's text has the value: only to keep your own value over it (`400 "Add a short note saying why the PDF text is wrong here."`).
  - Where it prints nothing parseable (a scan, a value the check didn't find, a yes/no or fixed-list pick): with either value, saying where the page prints it (`400 "Add a short note saying where the page prints this value. The PDF's text can't confirm it, so the approver relies on your note."`). The answer is marked `noPdfText: true`, and the approval page flags it "Not in the PDF text" with the value, the note and who answered.
- A pick on a value question or an interpretation is compared with the value held, like a typed one (not for `REQUIRED_MISSING`, an empty value or "not stated"): same → `matched`; else `differs`, both are shown, and the same pick again (or the read's) settles it with a note (`noPdfText`); another pick is checked again. Other picks are `chosen`. `cantTell` leaves it for the approver; any question left "can't tell" holds approval and counts in Needs you.
- A typed date must be a calendar day, `YYYY-MM-DD` (400 "That isn't a date. Pick the day the contract gives.").
- A settled answer writes its value into the master (validated against the schema first; a value that can't go there is a 400), marks the evidence `attested`, and adds the person to `editors`. Answering again re-checks it (`review.changed`). The same settling answer again, from the same person (same value or option, same note), changes nothing and logs nothing.
- `editors` (maker-checker): everyone who decides something; the typist of a contract typed by hand too. "Can't tell" adds nobody.
- Status codes: 409 not a draft, 404 unknown question, 400 a bad body (in plain words per field: `BODY_WORDS.answer`, `bodyProblem`) / no value / not a date / not an option / a note missing / doesn't fit, 409 a cap's limit or ratio while its kind is "No limit", 409 "as printed" with no printed total kept.

**"This looks wrong"** (`report`): only a single value (400 for an item or a section). On a draft, a blocking question (`reason: "reported"`); on one typed by hand only once typing is marked done (before, 409: change it in the form). 409 if the value is asked already (an open question, or a cap's limit while its kind is asked), and on a cap's limit or ratio while its kind is "No limit". On the live version, a correction draft: a copy of it (evidence and all, editors and questions empty) plus the question; the live version stays live until the draft is approved. While a newer version exists it's a 409 that says where to go: "The amendment in version N couldn't be read. Read it again, or type it in by hand, then report this on that version." (a failed read is read again, never replaced by a correction, or the amendment's terms would be lost); "Version N is being read right now…"; or "Version N is already in progress. Report it there." Logged as `number.reported` / `value.reported`, and the copy as `version.correction_opened`.

**Proofreading** stores `{ path, by, at }` marks, one per value, the latest. Any version with a master, signed ones too, never superseded (409). It never changes the numbers.

**Send back**: reopens answered questions (`outcome`, `answer`, `compare` cleared; `sentBack = { by, note, at }`), turns their `attested` evidence back to `conflict`, and raises a `sent_back` alert with the count and note, as written (everyone sees every alert; nothing is withheld, ADR-003). A term listed to bill by hand comes off the list while its answer is reopened. The log entry names the questions (`itemIds`). `refreshStudyStatus(…, { alert: false })` so the move back to Needs you doesn't also raise `questions_ready`. An unknown question is a 400; one not answered (or sent back already) a 409.

**Typing by hand**: `versions/by-hand` starts a blank draft (one empty budget grid, as the web's `blankRulebook`), replacing a failed version in place; 409 while a draft or a read is in progress. `PATCH .../values` types one value: every typed value is `attested`; a date must be a calendar day (400); a cap's limit or ratio can't be typed while its kind is "No limit", nor "No limit" picked while one is typed (409, `noLimitTyped`); the master must stay valid (400). Removing one row or visit moves the evidence of the ones below; adding or removing one is logged (`value.typed`) by the list's new length (`items`), not by value. Values only on by-hand drafts, and only until `by-hand/done` (`typingDone`), runs the contract checks on what was typed (asked as after a read), and asks every value nobody typed or picked (`missing:`, `REQUIRED_MISSING`, `placeholders`): the blank form has to fill what the schema allows no empty for, so nobody saw it. That's a number (a visit's total 0, a holdback's % 0), a yes/no or fixed-list default (a visit paid automatically, no overhead on a row, a fee billed one time, screen failures by invoice, "not stated"), and what the holdback is taken from. Done is its own mark, `typingDoneAt` on the version (column `typing_done_at`, migration 0012; by-hand drafts that already had questions were marked done then), never inferred from the questions: a contract typed in full has none to ask, and goes straight to approval. After that, a value is corrected with "This looks wrong". Until done, the draft counts as one thing that needs you, and approval is refused.

**Sign-off gate** (I1–I6): `signOffRefusal` in `@dct/shared` `answer.ts`, which the route refuses with (409) and the approve page explains with, so the two say the same. The first that fails, in this order:
- the version is a draft;
- `asOf` equals its `updatedAt`, so nothing changed since the approver opened it ("This contract changed since you opened it. Check it again.");
- typing by hand is marked done;
- **every** question is settled (`matched` or `chosen`), Review questions too: a "can't tell" holds approval until it's answered or sent back;
- every arm with budget grids bills one (`billedGrids`): an arm whose grids differ with none chosen bills nothing ("Choose which budget grid to bill for <arm>.");
- every evidence entry is `confirmed`, `confirmed_by_math` (the contract's own row, column, overhead and visit-total sums prove it) or `attested` ("n numbers aren't confirmed by the PDF, the contract's own totals or a person yet.");
- with maker-checker on (the default), the signer isn't in `editors`, names compared trimmed and ignoring case (`samePerson`).

**Nothing withheld** (ADR-003, 2026-11-01; replaces blind entry): every response, search, diff, audit entry and alert carries the values as they are, on a draft too. Each open question is shown with our reading and what we suggest (`suggest` in `@dct/shared` `answer.ts`, which the web calls): on a conflict, the PDF's printed text; on an ungrounded or scanned value, our reading; on an interpretation or yes/no, the read's pick; on a table check, the visit the read gave the column (`table.expect`, now sent); on a total that doesn't add up, the total as printed; on a date tied to the last signature, the e-signature record's latest date of signature (`signedOn`); nothing on a missing value, a money term, a blank check or which grid governs. Taking it sends the same answer typing or picking would, so it's checked, written and logged the same. `openPaths` (the open questions' paths and what they decide, `decidedBy`, and every `held` or `blank` value) marks values "needs you" in the web and refuses "This looks wrong" on them (409 "There's already an open question about this value.").

**`needs_you`** is computed in `refreshStudyStatus` only (`needsYouOf`), with `openCards` (`@dct/shared`), as the web's `needsYou`: the cards with a question not settled (no answer, `differs`, `cant_tell`, on any question, as the gate counts them); a by-hand draft still being typed (`typingDoneAt` null) counts 1. A card is the questions that cite the identical quote on the same page (`ReviewItem.cites`, set by `interpretations` on a question showing its clause: `{ documentId, page, quote }`; `cards`): the screen-fail clause's basis, cap and how it's paid, or fees whose trigger is one footnote. A money term's question (`UNACCOUNTED_TERM`) joins the first card whose quote is its sentence (`term.quote`) word for word, on any page of any document: an amendment that repeats the base contract's payment paragraph is one card per sentence. Spacing aside, never grouped by field name or alike wording; any other question is a card of its own. Each question on a card is still answered, checked and logged on its own (`POST …/review/:itemId`), and approval needs every question settled (`signOffRefusal` counts questions).

**Drafts saved before ADR-003** are read by today's rules wherever the API loads or returns a version (`upgradeReview`, applied in `loadVersion`, `versionDto` and `refreshStudyStatus`; signed and superseded versions as they are; the stored draft changes at its next write): an unanswered blind-sample or re-type question is dropped; a sample a person answered differently (a miss, or a first answer that differed) asks every value of its kind still only machine-checked and not proofread (`miss:<path>`, `SAMPLE_MISS`), as the old rule held approval for; a one-click "go ahead" on an unreadable page is asked again as today's page question, unanswered; a contract problem that's a notice now (`isNotice`) isn't asked.

## Writes: idempotency and atomicity

**`Idempotency-Key`** (IETF `draft-ietf-httpapi-idempotency-key-header`, Stripe's design; `src/lib/idempotency.ts`). Every POST and PATCH takes the header, as a structured-field string (`"…"`, what the web sends) or a bare token, 1–255 printable characters (else 400). The web sends a fresh UUID for each user action and the same one on its retries (`apps/web/src/lib/api.ts`).
- The write runs in one transaction, and the key, a fingerprint of the request (sha256 of method, URL and body; for an upload, its `by` and each file's name and sha256) and the response are saved **in that same transaction**: the write and its saved response commit together or not at all.
- Same key, same request: the saved response, byte for byte, with `Idempotent-Replayed: true`; nothing is written.
- Same key, different request: 422 "This Idempotency-Key was already used for a different request. Send a new key for each new action."
- Same key while the first is still running (a double click): the second waits on the key's advisory lock, then gets the first one's response. 409 "This request is still being processed…" if that takes longer than `DB_LOCK_TIMEOUT_MS`.
- A request that fails saves nothing (it changed nothing), so the same key runs it again once the problem is fixed, as Stripe's v2 does.
- Saved responses are replayed for 24 hours, then deleted by maintenance; a key used after that runs as a new request. A replay is the response as it was sent. They're kept in the same database as the versions.
- The header is optional: without it a write is applied each time it's sent, protected only by the natural rules below.

| Write | Sent twice without a key | With a key |
|---|---|---|
| POST `/uploads` | deduplicated by sha256 (no second row, file or log entry), but answered `duplicateOf` itself | the first answer (`duplicateOf: null`) |
| PATCH `/documents/:id` | the same kind again is a no-op (no log entry); a change logs one entry per study using the file | replayed |
| POST `/studies` | deduplicated by file set while the study is setting up (advisory lock); a second study once it has moved on | replayed |
| PATCH `/studies/:id` | the same details once confirmed: no-op (no log entry) | replayed |
| POST `/studies/:id/extract` | while reading, the same job (409 if it adds a file); after a failed read, **a second paid read** | replayed |
| POST `/studies/:id/versions/by-hand` | 409 "already in progress" (the first answer is lost) | replayed |
| PATCH `…/values` | the same value by the same typist is a no-op | replayed |
| POST `…/by-hand/done` | 409 "already marked done" (`typingDoneAt` is set) | replayed |
| POST `…/review/:itemId` | an answer that settled, sent again by the same person: no-op (no log entry). One that came back "differs", sent again (the same value or pick, or the PDF's own), **settles it** as chosen (with a note where one is needed); any other value is checked again, and comes back "differs" once more | replayed |
| POST `…/report` | 409 (an open question already; on the live version, the correction draft is in progress) | replayed |
| POST `…/proofread` | marks already there by the same person: no-op | replayed |
| POST `…/budget-check` | the same result again (the notice unchanged): no-op, nothing logged | replayed (the fingerprint holds the file's sha256) |
| POST `…/send-back` | 409 "Only answered questions can be sent back."; 409 for a table's columns (their answers are final) | replayed |
| POST `…/sign-off` | 409 "signed and immutable" | replayed |
| POST `/alerts/read` | no-op (`ON CONFLICT DO NOTHING`) | replayed |
| PATCH `/settings` | the same settings again: no-op (no log entry) | replayed |
| GET `…/export.xlsx` | each download is logged: it's an event of its own | not taken (GET) |
| jobs `identify`, `extract` | run once (Jobs, below) | — |


**Atomicity.** Everything one write changes is one transaction: the version, the study's status and needs-you count (`refreshStudyStatus`), the alert its stage change raises, its audit entries, its job and pg-boss job, and its saved response. Tests make the last insert fail (a trigger that raises) and check nothing was left: no status change without its log entry, no alert without its transition, no job row without its queued job, no file without its row (`test/atomicity.test.ts`). A job's result is one transaction too: a read whose completion fails ends `failed` with its log entry and alert, never a draft without them.

**Lock order.** Every write to a study locks it first (`lockStudy`, `SELECT … FOR NO KEY UPDATE`; `loadVersion(…, true)` does it), then its job's row, then its versions. Before, version routes locked the version and then the study while `POST /extract` and typing by hand locked the study and then the version: "This looks wrong" on a failed version at the same moment as reading it again deadlocked (reproduced; now tested). `NO KEY UPDATE`, not `FOR UPDATE`, so rows that only reference the study (audit entries, alerts) never wait for it. An idempotency key's lock comes before all of these.

## Running in production

- **Build**: `tsup` bundles `src/server.ts` and `src/db/migrate.ts` into `apps/api/dist`, with `@dct/shared` and `@dct/extraction` (TypeScript source) inlined, and their own dependencies with them (pnpm doesn't make those resolvable from `apps/api`). A banner defines `require` for the bundled CommonJS ones: without it exceljs failed at startup ("Dynamic require of "crypto" is not supported"), so the old build never ran. The mupdf worker isn't bundled and needs no build step: `@dct/extraction` resolves `mupdf-worker.mjs` through its own package exports, and mupdf from there (checked: the built server reads text layers and renders pages). Paths (`.env`, the migrations) are found by walking up from the running file, so they're the same from `src`, `dist` and any chunk.
- **Migrations are a separate step**, run before the new version starts (`node dist/db/migrate.js`), never on boot: on boot, every instance would race to run DDL, a slow migration would hold up readiness, a failed one would crash-loop the server, and the server would need DDL rights it otherwise doesn't. The migrator holds an advisory lock, so two runs at once apply each migration once. A server started on a database that's behind logs an error and stays not ready (`/readyz` `schema: "behind"`); it doesn't run maintenance on tables it doesn't know. pg-boss creates and upgrades its own `pgboss` schema at start, under its own lock, as it's designed to.
- **Shutdown** on SIGTERM or SIGINT: Fastify stops taking requests (new ones and `/readyz` get 503) and waits for the ones in flight, then pg-boss stops (up to 10 s for a running job), then the pool closes. Past `SHUTDOWN_TIMEOUT_MS` (30 s), or on a second signal, it exits anyway.
- **Logs**: JSON lines (pino) at `LOG_LEVEL`, each with its request's id (`reqId`, a UUID, also sent as `X-Request-Id`). Still the method and the route pattern only: no bodies, ids, query strings, contract text or amounts. Jobs and pg-boss log through the same logger; a pg-boss warning by its message only, never its data (a slow query's bound values, job ids).
- **Limits**: `REQUEST_TIMEOUT_MS` (120 s) for a whole request and an idle socket, `KEEP_ALIVE_TIMEOUT_MS` (72 s), 1 MB JSON bodies; an upload at most 50 files, 10 fields and 60 parts (413 in words). Database: `DB_POOL_MAX` (10) connections for the API and `JOBS_DB_POOL_MAX` (5) for pg-boss; each API connection has `statement_timeout` (`DB_STATEMENT_TIMEOUT_MS`, 30 s), `lock_timeout` (`DB_LOCK_TIMEOUT_MS`, 10 s) and a 60 s `idle_in_transaction_session_timeout`, and waiting for a free connection gives up after 10 s. An idle connection the database drops is logged and replaced (without a listener it would have crashed the process).

## Decisions

- **Study status is derived from versions** (`refreshStudyStatus`) after every version change, so it can't drift:
  - no versions → `setting_up`
  - latest version `extracting` / `failed` / `draft` → `extracting` / `extraction_failed` / `needs_review`, also while an earlier version is live, except:
  - a latest `draft` while an earlier version is live → `amendment_in_review`
  - latest version `signed` → `live`

  An amendment being read therefore shows as reading, and one that couldn't be read as couldn't read, with its alert, never as waiting for approval.
- **Jobs** (`src/jobs.ts`, pg-boss queues `identify`, `extract`, `stranded`, `maintenance`):
  - Our `jobs` row id is the pg-boss job id. It holds state, progress and step for `GET /jobs/:id`.
  - **Queued in one transaction**: the row and its pg-boss job are inserted in the request's own transaction (`queueJob`, pg-boss `send` with `fromDrizzle(tx)`), so a job row is never left "queued" with nothing to run it. Before, the job was sent after the commit, and a server stopping in between left a study setting up, or a read extracting, for ever.
  - **Runs once**: `extract` claims its row (`queued` → `running`) in one conditional UPDATE, so a second delivery of the same job, at once or later, does nothing: one AI read paid for. `identify` may run again after a crash (it's cheap), but only one run writes: its result's transaction locks the row and goes on only while the job is still live. A read's result is written only while its job is still `running`, so a read declared dead meanwhile (below) is dropped, never written over the failure.
  - **At most one live read per version**, by the database too: a partial unique index on `jobs (study_id, version)` for `extract` jobs `queued` or `running` (migration 0009).
  - **Not on a database that's behind**: no worker and no schedule start while migrations are pending (`jobs not started: the database is behind this build`); migrate, then restart.
  - **Retries**: `identify` 2, 5 s apart (crashes). `extract` 0: each try pays for AI reads, so a read that failed is read again only when a person asks (`POST /extract` reuses its version). An extraction error marks the version `failed` with plain words and the technical detail, which never quotes the model's reply.
  - **A job whose server died is failed, never left running**: workers heartbeat every 30 s (`heartbeatSeconds: 60`); pg-boss's supervisor (every minute) fails a job that missed its heartbeats, or that ran past `expireInSeconds` (identify 15 min, extract 2 h), and copies it to the `stranded` dead-letter queue. Its worker marks our row failed (`recover`) and, for a read, the version too, with the study's status, the "couldn't read" alert and an `extraction.failed` entry, in one transaction: "The server stopped while reading this contract, so the reading didn't finish. Read it again, or type it in by hand." (or "took more than two hours"), detail `pg-boss: job heartbeat timeout`. A time-out (pg-boss's supervisor says `job timed out`; the worker running it, `handler execution exceeded …`) gets the "took more than two hours" words. A crash is found within a minute or two of the next start.
  - **An abandoned read stops**: `runExtract` gets the pg-boss job's abort signal. Once pg-boss gives up on the job (past its time, its claim lost, a shutdown), the read starts no further AI call and cancels the one in flight (`capped` in `@dct/extraction`), never writes its result, and doesn't fail the job itself: the stranded queue does, in the words above.
  - **Maintenance** (`maintain`, at startup before any job runs, then every 10 minutes): a live row whose pg-boss job has ended or is gone is failed the same way (the backstop for a stranded job that couldn't be handled, and for jobs from before queueing was transactional), and so is a version `extracting` with no live job. It also deletes idempotency keys older than a day.
  - On SIGTERM, pg-boss gets up to 10 s to let a running job finish; one still running is failed by pg-boss into `stranded`, so the next start marks it.
  - A handler that throws gives pg-boss a plain error (the database error's code, never its SQL or values), since pg-boss stores it and copies it into the stranded job.
  - NOTIFY wakes a worker as soon as a job is sent; a 1 s backstop poll keeps a backlog moving (pg-boss's 30 s default would start one job of a backlog every 30 s).
  - Settled jobs are deleted by pg-boss after 7 days (its default); our `jobs` table is the lasting record.
  - `POST /extract` on a failed version reuses the same version number, so a retry never creates a duplicate; while a version is extracting it returns the same job; while a draft exists, 409.
- **Signed is immutable twice over:**
  - The API returns 409 on any write to a version that isn't a draft (proofreading aside).
  - A DB trigger refuses changes to signed/superseded rows, now including `evidence`, `review`, `pdf_check` and `by_hand`. The only changes it allows are `signed → superseded` and `proofread`. TRUNCATE skips row triggers, so a statement trigger refuses it while any version is signed or superseded (migration 0011).
  - The previous live version becomes superseded in the same transaction as the new sign-off.
- **Audit log is append-only by trigger**, TRUNCATE included (0011). Every write that changes something writes an entry (a write that changes nothing, such as the same settings again, logs nothing), in the same transaction as the change. Uploads, study creation and job results use `by: "system"` unless a `by` is given.
- **Upload text detection:** after the PDF is stored, its text layer is read: `text` when any page has real text, else `scan`; null when mupdf can't read its text (a file it can't open at all is refused at upload, below; the read then fails with the reason). Files uploaded before this stay null ("not known yet").
- **Diff:**
  - Items in rulebook arrays are matched by identity (id, then code, name, label, kind, description), not by index.
  - `prov` subtrees are ignored, and `{value, prov}` collapses to the value.
  - Labels read section first with ` › ` separators, e.g. `Invoiceable › Unscheduled visit › Amount with overhead` (the web groups by the first part). The same labels name values in "This looks wrong" questions. `diffRulebooks` and `labelFor` are in `@dct/shared` (`diff.ts`).
  - `before` is the `against` version.
- **Uploads:**
  - Only PDFs are accepted: the `%PDF-` magic must be present (else 415), and mupdf must open the staged file and count its pages, in its worker (`pageCount` through the port): 400 "<file> could not be read as a PDF" if it can't, 422 "<file> took too long to open, so it wasn't uploaded…" if not within 30 s. A crafted PDF then costs a time-out in the worker, never the event loop. The worker loads a page before counting, so a `/Count` that claims more pages than the page tree holds is corrected: the upload, the read and the page viewer agree. A file already stored (same sha256) isn't counted again. pdf-lib is only a test dependency now.
  - The size limit is 50 MB (413 "This file is bigger than the 50 MB limit. Send a smaller copy: a long PDF split into parts, or a spreadsheet with only its budget sheet."), at most 50 files per request (413 "Upload at most 50 files at once."), 60 parts and 10 fields (413 in words), and 100 pages per PDF (422 with what to do; the reading's own limit). `app.ts` words `@fastify/multipart`'s limit errors by their codes.
  - All of a request's files or none. Each is staged as `<UPLOAD_DIR>/<sha256>.pdf.<uuid>.tmp`, flushed to disk (fsync), and its text layer read from there. Then one transaction locks every file's sha256 first, in sha256 order (advisory locks; two uploads sharing files in opposite orders used to deadlock), inserts the rows and audit entries, saves the response for its idempotency key, and, last, renames each staged file to `<sha256>.pdf` and flushes the folder. A failure before the commit removes any file it put in place, so a failed insert never leaves a file under its final name; the staged files are removed either way.
  - A crash between the rename and the commit can leave `<sha256>.pdf` with no row. It holds exactly those bytes, so the next upload of them takes it over (tested). Nothing deletes files in the upload folder by itself (it holds the contracts).
  - A duplicate returns the existing document with `duplicateOf = existing id`. The original filename is kept.
- **Page images** are cached at `<UPLOAD_DIR>/pages/<sha256>-<n>.png` (`@<dpi>` for the other sizes: a requested DPI is rounded up to 72, 150, 220, 300 or 400). The browser keeps one for an hour (`private, max-age=3600`). A page that takes too long to draw gets 422 and isn't tried again until a restart.
- **mupdf runs in a worker thread** (`packages/extraction/src/mupdf-worker.mjs`): page images, page text and the text layer. A call longer than `RENDER_LIMITS.timeoutMs` (30 s) is stopped and the worker replaced, so a crafted PDF can't freeze the server. At most 8 PDFs stay open.
- `appliesFrom` on a version is `rulebook.appliesFrom.value`, falling back to `study.effectiveDate.value`; answers and typed values keep it current.
- **A bad body is a 400 in plain words.** The review bodies (an answer, a typed value, a report, proofreading, a send-back, typing by hand) name the first bad field (`BODY_WORDS`, `bodyProblem` in `@dct/shared`). So do sign-off, creating, confirming and reading a study, a document's kind, settings, marking alerts read and the budget check's `by`. Queries (lists, search, audit, alerts) still go through `parse()`, whose 400 is zod's `prettifyError` text.
- **`updatedAt` moves forward on every write** to a version, by at least a millisecond (`touched` in `domain.ts`), so `asOf`, compared to the millisecond, can't miss a write made in the same millisecond as another.
- Names are compared as `samePerson` compares them (trimmed, ignoring case) in maker-checker and in whether an alert is read for a person (they caused it or marked it).
- A malformed uuid in a URL returns 400, not 500, and so does a version number over 9 digits (checked once, in a `preValidation` hook). Postgres errors a request causes (`22P02`, `22003`, `22007`, `22008`) are 400 too. A write rolled back by a concurrent one (`40001`, `40P01`, or a lock wait past `DB_LOCK_TIMEOUT_MS`, `55P03`) is 409 "Someone else was changing this at the same moment, so nothing was saved. Try again."
- **A repeat that the state has moved past is a 409**, with what to do: sign-off of a signed version, typing done twice, a second report on a value with an open question, sending back a question that isn't answered (it was 400; an unknown question id stays 400).
- **A server error (5xx) never shows its cause**: the response says "Something went wrong on the server… (ref <request id>)". A database error's message is the SQL with every value bound to it, so the log gets the query and the cause only, never the values. Failed jobs say the same for a database error.
- Request bodies are at most 1 MB (uploads have their own limit). Every response has `X-Content-Type-Options: nosniff`, and JSON is `Cache-Control: no-store`. The request log is the method and the route pattern: no ids, query strings or bodies.
- **Study details lock once a version is approved**: `PATCH /studies/:id` returns 409. The export is named and headed from the approved version's own study details, never the editable study row.
- **No login yet: this computer only** (user decision 2026-10-28). The API listens on 127.0.0.1 (`config.listenHost`) and so does the web app (`-H 127.0.0.1` in every `apps/web` script). Every `by` is the name someone picked, so anyone who can reach the app can approve as anyone, mark alerts read for anyone, and turn maker-checker off. **Before it listens anywhere else, or more than one person uses it, add login** and take `by` from the session.
- **Host/Origin guard**. It is an `onRequest` hook in `src/app.ts`, so `fastify.inject` tests exercise it.
  - Any request whose `Host` is not in `ALLOWED_HOSTS` gets 403 (DNS rebinding), and so does one whose `X-Forwarded-Host` isn't: the Next proxy always sends the API's own Host and moves the browser's there, so without it a rebinding attack on the web port would read everything. The default allows `localhost` and `127.0.0.1` on port 4100 and on port 3100.
  - A POST, PATCH, PUT or DELETE whose `Origin` is present but not in `ALLOWED_ORIGINS` gets 403 (CSRF). The default allows `http://localhost:3100` and `http://127.0.0.1:3100`, and `Origin: null` is rejected.
  - A request with no `Origin` passes (curl, server-to-server).
  - Both lists are comma-separated env vars.
- No CORS is set. The web app proxies `/api` with a Next rewrite to the API.
- **Migration `0011`** refuses TRUNCATE on `audit_log` always, and on `rulebook_versions` while any version is signed or superseded, with statement-level triggers (TRUNCATE skips the row triggers of 0001 and 0006; a `TRUNCATE studies CASCADE` reaches them too). The API tests' `resetDb` turns them off inside its own transaction.
- **Migration `0010`** adds `rulebook_versions.warnings`, makes maker-checker default to on, and turns it on in a database whose audit log is empty (a database in use keeps its setting).
- **Migration `0007`** indexes `audit_log (study_id, id)` for one contract's log, paged newest first. `GET /audit` pages by id (keyset cursor, as `/studies` and `/alerts`); `q` is an ILIKE over the person, the action (its code or its `ACTION_LABELS` name) and every text and number in the details.
- **Migration `0006`** locks a signed or superseded version as a whole row: only signed → superseded, `updated_at` and `proofread` may change, and it can't be deleted (0005's trigger listed columns, so `version`, `study_id`, `sign_note` and the rest could still change).
- The `extract` queue never retries (each try pays for AI reads; a crashed read is failed in plain words and read again from the contract page) and a read may run 2 hours. `identify` keeps 2 retries.
- **Migration `0005`** marks every draft that existed before it `failed` ("Read before every number was checked against the PDF. Read it again."): it has no questions, so it would have gone straight to approval unchecked. The contract page then offers "Read it again" or typing it in by hand.

## Added at integration testing

- **Amendment extraction carries the live version's corrections forward** (`runExtract`, only when a signed version exists). The amendment's values win; the live version's corrections fill in where it didn't change anything, and the result is checked against the PDF like any read:
  - **Values: replayed from the audit log**, not stored on the version. `correctionsOf(live)` = what the live version carried at extraction (`version.corrections_carried`) + what a draft inherited by copying a live version (`version.manual_created` / `version.correction_opened` with `seededFromVersion` → recurse) + its answers that wrote a value (`review.answered` / `review.changed` with `after`) + `value.corrected` entries from before review questions existed, oldest first. So corrections carry transitively v1 → v2 → v3.
  - Each correction applies only if the new read's value at its pointer deep-equals the correction's `before`, **and** the array items on the path have the same identity as when it was made (`items`, e.g. `["g2","V2"]`). Applied values get `prov.method = "manual"`; carried corrections don't add editors.
  - Skipped with a reason: `amendment_changed`, `item_moved`, `path_missing`, `invalid`, `already_equal`. Every one but `already_equal` is said on the draft and asked again (Review questions, item 6).
  - **Grid, per arm** (`carryGrid`): an arm's live choice is carried only when the new read has the same grid labels for that arm, and its id goes into `governingGridIds`. An amendment that adds, drops or renames one of the arm's grids asks its `GRID_CONFLICT` again. (A grid pick is logged as `gridId`, not as a value, so only this carries it.)
  - Answers to contract-problem questions are not carried, nor is the bill-by-hand list: the amendment asks them again (its read finds the same terms unaccounted).
  - One audit entry `version.corrections_carried` `{ version, from, carried[], skipped[], grid: {from[], to[]} }`; each skipped one has its `reason`, and `askedAt` where it's asked again.
- `POST /studies` with a file set that a `setting_up` study already has returns that study (double-click safe).
- `GET /audit` is newest first.
- Fake mode renders real page images and reads the real text layer; a filename containing `unreadable` makes the fake extraction fail. The fake read cites page 1 (terms) and page 2 (grids) of the first document; `apps/api/test/helpers.ts` `makeTextPdf` prints a matching born-digital work order, with one titled table per fake grid on page 2, as a contract prints an exhibit and its revision.

## Known gaps

- A yes/no or fixed-list answer is compared with the value held, like a typed one ("This looks wrong", an interpretation): a different pick `differs`, a second pick settles it.
- Arithmetic questions are suppressed per grid, not per visit.
- A correction from the live version on a total that the amendment's read confirms, but whose parts don't add up there, isn't asked: the total's "which should we bill" question stands for it. The draft's warning still says it's "asked again in Needs you".
- A version approved before `d5e8169` with an arm whose grids differ and no grid chosen (none exists yet): the Excel export's Budget grid sheet marks each such grid "NOT BILLED: no grid was chosen for this arm", but its Summary sheet lists every grid's per-patient total without saying none is billed.
- The binder's own limits (a fee's name on the line above another term's amount, misread grid cells, amounts the sweep doesn't see) are in [ADR-001's implementation notes](adr-001-extraction-evidence.md#implementation-notes-2026-10-29).
